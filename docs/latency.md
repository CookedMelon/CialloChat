# 服务端转发延迟

范围修订：用户要求专注推流工具与服务端，不再分析或调整播放器。用户反馈 FFplay 参考窗口约 1.7 秒，比 VLC 的约 0.8 秒更慢；不能确定延迟全部属于播放器。以下编码/解码及图形播放器对照只保留为历史证据，新的验收以协议层压缩帧转发测量为准。

用户实测：OBS 推流到本地服务，PotPlayer 持续落后至少约 2 秒；换用 VLC 后明显改善。VLC 命令始终包含 `--network-caching=100`，秒表测得仍约 0.8 秒。切换 x264、NVENC H.264、AMD H.264 未消除问题。不能再把“忘记设置 VLC 缓存”当作默认原因，也不能仅凭更换编码器排除它们共同使用的缓冲设置。

## 当前使用的协议层测量

入口：[scripts/measure-forwarding.sh](../scripts/measure-forwarding.sh)。Go 1.26+ 仅是可选开发验证依赖，不进入 setup 或生产服务依赖；使用与锁定 MediaMTX 匹配的 gortmplib/gortsplib 版本，依赖由 go.mod/go.sum 锁定，编译缓存和二进制均存于项目 runtime。脚本不安装系统软件。

```bash
./scripts/measure-forwarding.sh --seconds 60 --report runtime/reports/forwarding-single.json
./scripts/measure-forwarding.sh --seconds 60 --readers 4 --report runtime/reports/forwarding-four.json
./scripts/measure-forwarding.sh --seconds 60 --readers 4 --slow-reader --report runtime/reports/forwarding-slow-reader.json
```

使用独立测试容器、临时账号和随机回环端口。FFmpeg 先生成 3 秒 1440p/60、目标 6 Mbps 的 H.264/AAC 素材，编码完成后退出；随后测试进程按预编码时间戳循环发布。循环音视频边界使实际目标视频速率约为 59.45 fps，该速率与实际接收速率一并记录，不冒充严格 60.00 fps。

计时从每个压缩视频帧执行 RTMP 写入前开始，至 RTSP/TCP 端收齐同一帧的 RTP 包为止。首次用 VCL NAL 内容 SHA256 唯一匹配对齐 RTP 时间戳，之后要求每一帧的时间戳与内容哈希同时匹配；SPS/PPS/AUD 等封装可变项不用于图片内容匹配。测试只做 RTP 拆包，不解码画面、不显示视频。发布端与接收端共享同一进程的单调时钟，不存在跨主机校时误差。

报告包含协议序列化、本地 TCP/Docker 网络、MediaMTX 转发和 RTP 拆包，因此是**协议转发路径耗时**，不是精准的服务进程内部函数耗时；不包括 OBS 采集/编码、播放器解码/同步/显示，也未测量音频延迟。AAC 与视频一起传输，以保留音视频封装条件。每个正常读者检查接收速率和内容匹配；最新探针同时检查稳态序号缺口、重复与乱序。

慢读者场景额外建立一个 RTSP/TCP 连接，每收到一个 RTP 包故意阻塞 300 ms；该读者本身不计入正常读者的延迟统计。验证目标是慢读者不能拖慢其余读者，允许慢读者被丢包或断开。可用 `--queue-size` 对隔离测试实例设置输出队列大小，不修改业务服务。

### 服务端配置决策

媒体保持直接转发；Python 只执行管理操作。没有新增转码、录制、切片等待或按固定时间缓存。当前继承锁定 MediaMTX 的输出队列 512、写超时 10 秒；这些值分别是队列容量与阻塞写操作超时，**不表示每帧等 512 个包或等待 10 秒再发**。当前低负载协议测试未显示固定的秒级服务端等待，不以随意缩小队列或超时宣称降低延迟；关键帧突发、慢读者隔离和内容完整性必须同时考虑。[锁定版本配置定义](https://github.com/bluenviron/mediamtx/blob/v1.21.1/mediamtx.yml)

### 旧版协议基线（2026-10-03）

每组目标采样 60 秒，实际视频约 59.45 fps，素材平均约 6.36 Mbps（含 FLV 音视频封装，后两项元数据从最新慢读者场景直接记录）。所有正常读者均实时匹配到相同压缩视频帧。

| 场景 | 正常读者合计样本 | 各读者中位数范围 | 最高读者 P95 | 最大单帧耗时 |
| --- | ---: | ---: | ---: | ---: |
| 1 个正常读者 | 3,625 | 0.463–0.463 ms | 0.631 ms | 1.350 ms |
| 4 个正常读者 | 14,504 | 0.599–0.623 ms | 0.856 ms | 4.157 ms |
| 4 个正常读者 + 1 个慢读者 | 14,504 | 0.589–0.615 ms | 0.820 ms | 2.082 ms |

三组均无内容哈希或时间戳匹配错误。慢读者组使用增加序号连续性检查后的探针，4 个正常读者的稳态丢帧、重复、乱序均为 0；前两组只记录匹配错误与接收速率，没有序号丢帧字段，不把缺失字段当作已测量为 0。没有观察到慢读者导致正常读者产生秒级积压。

完整逐帧证据：[单读者](evidence/forwarding-single.json)、[四读者](evidence/forwarding-four.json)、[额外慢读者](evidence/forwarding-slow-reader.json)。这是所测本地负载下的结果，不是公网、任意带宽或任意并发量的保证，也没有证明用户此前画面延迟的具体归属。

这些结果支持保留当前直接转发方式与锁定版本的队列默认值。此次新增的是协议层性能验证和明确验收边界，未宣称通过更改配置消除了此前播放器中的秒级显示延迟。

## 双密钥版本协议验收（2026-10-03）

启用 schema 2 独立推流与观看认证，使用最新探针复测三个场景，每组目标采样 60 秒。观看认证和最初的媒体对齐不混入稳态每帧统计。素材、帧率、测量边界与上述方法一致；每个正常读者都检查丢帧、重复、乱序和内容匹配。测量期间另有隔离部署验证运行，因此本轮统计包含同机后台负载，不作严格空载前后性能比较。

| 场景 | 正常读者合计样本 | 各读者中位数范围 | 最高读者 P95 | 最大单帧耗时 |
| --- | ---: | ---: | ---: | ---: |

完整证据：[新版单读者](evidence/forwarding-v2-single.json)、[新版四读者](evidence/forwarding-v2-four.json)、[新版慢读者对照](evidence/forwarding-v2-slow-reader.json)。这是本机所测负载下的协议路径耗时，不是播放器画面延迟或公网承诺。

## 历史：包含编码与解码的测量


`scripts/measure_latency.py` 使用独立 Compose 项目、临时账号、随机回环端口和当前锁定镜像。它不会修改业务账号、业务容器或 Windows 客户端；结束后清理测试容器。

```bash
PYTHONPATH=src .venv/bin/python scripts/measure_latency.py \
  --ffmpeg /路径/ffmpeg --seconds 60 \
  --report runtime/reports/latency-compose.json
```

可额外传入 `--mediamtx /路径/锁定版本的mediamtx`，在本机原生进程上运行同一测试，以比较 Docker 路径；这不是生产部署方式。

测量过程：

1. Python 在同一主机的单调时钟上记录帧生成时间，把帧编号和逐位取反的校验值编码到画面条纹中。
2. FFmpeg 以 720p/30 fps、x264 veryfast/zerolatency、B 帧 0、1 秒关键帧、目标 2 Mbps 编码，同时携带 AAC 48 kHz/128 kbps 音频，经 RTMP 发送给 MediaMTX。
3. 第二个 FFmpeg 使用 RTSP/TCP 和低缓冲解码参数，解码画面中的帧编号；Python 记录解码数据到达时间，与该帧生成时间相减。解码后的编号必须通过取反校验，不接受重复、未知或损坏的帧编号。
4. 首帧等待单独报告。首帧后的 2 秒作为预热，再采集 60 秒，输出逐帧样本、中位数、P95、最大值和前后段中位数；不足预期帧数 80% 则报错，不以少量幸运样本得出结论。

该数值包括合成帧生成、编码、进程通信、RTMP、MediaMTX、RTSP/TCP 和视频解码，**不是单独的服务器转发耗时**。没有测量 Windows OBS 的采集和发送、VLC/PotPlayer 的音视频同步和显示、显示器延迟，也没有测音频延迟。画面为低复杂度合成图案，不能代表高运动/高码率负载。读者不按显示时钟播放，不能把结果当作 GUI 播放器承诺。

如该链路实测显著低于 0.8 秒，只能证明在所测负载与参数下没有固定 0.8 秒的服务链路下限；实际 OBS/VLC 链路仍需定位。当前按修订范围只测协议转发路径，不再要求用户配合播放器秒表对照。不能用空闲 CPU、连接成功或首帧出现代替稳态逐帧测量。

## 2026-10-03 实测结果

| 路径 | 稳态样本 | 中位数 | P95 | 最大值 |
| --- | ---: | ---: | ---: | ---: |
| WSL FFmpeg → Docker MediaMTX → WSL FFmpeg | 1,808 帧 | 40.691 ms | 126.544 ms | 276.352 ms |

60 秒稳态采样，损坏编号为 0，前/后段中位数为 40.889/40.583 ms，没有观察到逐步累积的延迟。首帧等待为 926.488 ms，单独列出，不与稳态延迟混用。完整参数与逐帧样本见 [测量报告](evidence/latency-compose.json)。

该结果说明本次合成流条件下服务链路没有固定 0.8 秒延迟下限。用户测得的 OBS → VLC 约 0.8 秒仍未解决，不能把该数值与此处中位数直接相减，声称差额全部来自某一个客户端。实际链路还包含不同的采集、编码、网络路径、音视频播放同步与显示。

### 实际 OBS 流与高分辨率对照

用户重新推流后，只读探测得到 H.264 High、2560×1440、平均 60 fps、B 帧 0、AAC LC 48 kHz 双声道。10 秒媒体时间内采集 602 个视频包，帧时间戳增量为 16–17 ms，无倒退，视频约 5.96 Mbps。采样中相邻关键帧相隔 4.166 秒，这影响加入等待，不能解释为每帧固定延迟 4.166 秒。采样时服务 CPU 约 1.93%，仅为单次观察。见 [码流元数据](evidence/obscheck-timing.json)；未保存用户画面或音频内容。

第一轮 1440p/60 合成对照沿用 veryfast、2 编码线程：中位数 591.101 ms、P95 679.770 ms，但实际仅 49.86 fps，未实时跟上目标 60 fps。因此这份报告包含测试端过载/排队，不能拿来宣称 MediaMTX 存在约 0.6 秒转发延迟。原始样本保留于 [未达到实时速率的对照](evidence/latency-compose-1440p60.json)。测量脚本已增加 `measured_fps` 与 `kept_realtime` 标记；低于目标速率 95% 时不作为实时延迟验收通过。

第二轮仅调整合成测试的编码配置为 ultrafast、4 线程：实际 60.146 fps，60 秒采集 3,610 帧，中位数 **30.255 ms**、P95 **48.404 ms**、最大 **174.875 ms**，未出现损坏编号。见 [达到实时速率的 1440p/60 对照](evidence/latency-compose-1440p60-fast.json)。这一结果不包含 OBS 的真实采集/编码或 Windows 播放器；两轮测试不能证明用户的 OBS 正在过载，但说明工具自身是否实时必须单独检查。

## 历史播放器观察

用户观察 PotPlayer 持续落后约 2 秒、VLC 设置 100 ms 网络缓存时约 0.8 秒、FFplay 参考窗口约 1.7 秒。这些包含采集、编码、传输、解码与显示，未定位全部延迟来源。已停止播放器调优，不再要求使用 `play-low-latency.sh` 或继续切换播放器；项目验收仅采用上面的服务器协议转发测量。
