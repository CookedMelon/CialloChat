# RTSP 缓冲与延迟

当前正式方案保留内网长期测试采用的 **1000 ms 固定缓冲**。不根据码率自动扩大窗口；码率决定所需内存和带宽，突发的时间跨度决定时间缓冲是否足够。当前 3200 Kbps 视频＋160 Kbps 音频的一秒媒体约 420 KB，单观看连接默认 8 MiB 队列另留拥塞余量；这是内存上限，不是额外固定播放延迟。

## 保留的机制

- 每位读者独立接收与发送队列，网络读取不会被等待发送时间的任务阻塞。
- 按 RTP 时间戳匀速发包，视频与音频分别使用 SDP 的 90 kHz / 48 kHz 时钟。不同轨道即使使用相同 PT，也不共享时钟。
- 保持压缩媒体、RTP 序号与媒体时间戳不变；RTCP Sender Report 的墙钟同步增加相同缓冲时长，并还原读者反馈中的 LSR，避免虚假的上游 RTT。
- 启动时预填缓冲；保活响应不等待媒体队列，避免人为触发播放器超时。
- 每连接默认最多缓存 8 MiB；连续无写入进展超过 10 秒、单次写入等待达到 30 秒、队列超限或源时钟出现大幅跳变时关闭该连接，不丢弃任意 H.264 碎片继续播放。短时拥塞恢复后按原定发送时间追赶，实际播放恢复速度取决于网络和播放器。参数与诊断日志见 [部署说明](deployment.md#观看链路拥塞恢复)。
- 全部账号合计最多八个缓冲观看连接；每来源每分钟最多三十次新连接。尚未鉴权的连接八秒超时，拒绝大消息体和上传媒体。

该实现没有自适应窗口、转码、编码降码率，也不会检测客户端显示画面是否冻结。低至 300 ms 的窗口未通过此前房间测试，已移除试验入口。

## 可观察边界

`runtime/reports/rtsp-buffer.jsonl` 每两秒记录排队字节、音视频尚未发出的媒体时间、发送迟到和网络写入耗时。日志最多约两份 1 MiB 文件，不保存媒体或密码。

这些指标能识别服务端缓冲与发送阻塞；即使其正常，也不能证明 VRChat 解码、渲染及内部缓存正常。此前用户对照发现 VLC 短暂卡顿后较快恢复，VRChat 恢复更慢，最后两者时序相近；恢复期间没有介入重启服务或主动踢掉正常观看连接。最终用户确认当前方案可稳定使用。

一秒缓冲是服务端增加的时间，OBS 采集/编码、关键帧等待、播放器缓存与显示仍会增加延迟。此前用户观测端到端约两秒或 2.4 秒，不能据此承诺所有播放器的固定总延迟。公网最终部署仍需实际 OBS/VRChat 验收。
