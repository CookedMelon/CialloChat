# 2K 屏幕推流与服务端码率限制

这里的 2K 指 2560×1440。优先保持原始输出分辨率，避免先缩小再放大导致文字模糊。下列参数针对 SDR、H.264 和 AAC，兼顾现有播放器兼容性；不保证每个场景都无损。

| OBS 项目 | 建议值 |
| --- | --- |
| 基础/输出分辨率 | 2560×1440 |
| 帧率 | 60 fps；静态桌面可选 30 fps |
| 视频编码 | 可用的硬件 H.264 编码器 |
| 码率控制 | CBR |
| 视频码率 | 34000 Kbps（60 fps）；21000 Kbps（30 fps） |
| 音频 | AAC，192 Kbps，48 kHz |
| 关键帧间隔 | 1 秒 |
| B 帧 | 0 |
| Look-ahead | 关闭（编码器提供该项时） |

YouTube 当前 H.264 直播建议为 1440p/60 fps 34 Mbps、1440p/30 fps 21 Mbps，可作为高画质输入的参考。这里使用这些码率，关键帧和 B 帧另按低延迟目标选择，未照搬平台的全部编码参数。[官方码率表](https://support.google.com/youtube/answer/2853702?hl=en)

6000 Kbps 可以编码 1440p，但快速变化、细小文字和复杂纹理更容易出现压缩损失。码率提高不能恢复已缩小或模糊的原始画面，也不能保证屏幕文字无损；需要用实际桌面和动态内容验收。Python 不编码或转码，服务端不会把 34000 Kbps 降成更低码率。

## 自动断连

默认每个发布连接的上限为 **45000 Kbps**，十进制单位（1000 bit/s），比 34000 视频 + 192 音频留约 32% 余量。上限依据 MediaMTX 的 `inboundBytes`，包括该连接音视频和协议接收数据。不会把同路观众数乘进发布码率，也不会把多路推流合并后误断一人。

独立 watchdog 每秒采样，通过累计接收字节差计算最近约 5 秒的平均码率；窗口至少满 5 秒，连续两次采样 **大于** 上限即调用本机 Control API 断开该发布连接。稳定持续超限一般在被观察到后约 6–7 秒断开；API 处理或调度异常时不能保证这个时限。单个关键帧峰值不会因为瞬时超限直接触发断流，但足以使完整窗口持续超限的突发也会被限制。此处是平均码率断连策略，不能替代逐包硬限速。

覆盖 RTMP、RTMPS 及已获推流授权的 RTSP 发布连接，观看连接不参与判定。其他发布者保持在线；账号和密钥不改变。发布停止后读者会收到流结束。OBS 自动重连仍超限则再次被断开，应调整码率，而不是靠重连绕过限制。

监控只读取计数器，不接收、排队或缓冲媒体。这 5 秒是测量窗口，不会给画面增加 5 秒等待。watchdog 无公网端口，只在内部网络访问媒体 API；其专用配置包含管理凭据，保存在 `runtime/watchdog/config.json`，权限 600，不提交 Git。鉴权容器不挂载这份明文凭据。容器故障由 restart 策略重启；连续监控失败退出，健康检查不会将失败视为成功。重启后重新积累窗口，监控故障期间不能保证超限断连。

查询及调整（运行中可调整，不必重启直播）：

```bash
./streamctl limits
./streamctl limits --publish-kbps 45000
```

上限不能设为 0 或关闭。旧设置没有该字段时也使用 45000 Kbps，旧备份恢复不会回到无限制推流。修改值保存在 settings.json；启动和恢复后生成专用监控配置。

## 200 Mbps 出网预算

34000 视频 + 192 音频，每个观众约需 34.2 Mbps，再加协议开销。单路五名观众约 171 Mbps，接近 200 Mbps；四名观众约 137 Mbps，留有更充分余量。每路 45 Mbps 的上限保护单个发布者，不是全服务器 200 Mbps 的总出网限速，也不限制观众数量。观看端也需要足够带宽。
